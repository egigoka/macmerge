# Windows Shell and Integration Scope

MacMerge is a native macOS application, not a binary-compatible host for WinMerge's Windows integration components. This document records Windows source behavior, current native outcomes, intentionally unsupported policy, and gates for future work.

This scope implements the decision requested by [Milestone 6](../todo.md#milestone-6-extended-winmerge-parity) and uses the [parity ledger vocabulary](../todo.md#windows-to-mac-ui-parity-ledger) exactly. `N/A` means a Windows-only mechanism has no macOS meaning; it does not mean deferred, missing, or rejected. Every portable user outcome is classified separately as `MAC_ADAPTATION`, `PARTIAL`, or `MISSING`. "Intentionally unsupported" records a product or security decision rather than redefining `N/A`.

## Intentionally unsupported scope

MacMerge will not ship or emulate:

- Windows shell-extension DLLs, COM class registration, CLSIDs, registry-backed shell state, `regsvr32`, or Windows 11 sparse-package deployment.
- Explorer `IContextMenu` or `IExplorerCommand` handlers, arbitrary hosted third-party shell menus, Windows Jump Lists, shell links, AppUserModelIDs, or taskbar COM.
- Global `PATH` mutation, **App Paths**, or installer-written Tortoise configuration.
- OLE drag/drop transport, `SHFileOperation`, `IFileOperation`, or Recycle Bin APIs.
- COM/ActiveX/VBScript/scriptlet loading, WinMerge's `IMergeApp` host ABI, or compatibility with Windows plugins.
- Generic arbitrary shell-command execution or in-process third-party execution as a substitute for missing integration.

These exclusions concern platform mechanisms or explicit security/product decisions. Finder opening, command-line discovery, external diff-tool invocation, projects, native recents, pair/folder history, Dock tasks/progress, Services, drag and drop, Trash, and safe extensions remain separately classified outcomes above.

## Rationale and security boundaries

Windows shell and COM interfaces depend on Explorer, registry activation, Windows object models, and Windows process contracts. Reproducing those transports on macOS would add compatibility code without native behavior. Legacy in-process shell handlers and WinMerge's script/plugin host also execute third-party code with broad ambient access; Windows 11's surrogate hosting reduces Explorer-process coupling but does not create a portable MacMerge extension contract.

MacMerge keeps these boundaries:

- The default packaged configuration enables App Sandbox, user-selected read/write access, and app-scoped security bookmarks ([entitlements](Packaging/MacMerge.entitlements), [packaging script](Scripts/package-app.sh)). `swift run MacMerge` is unsandboxed. `package-app.sh` also accepts an **ENTITLEMENTS** override and currently verifies required keys without rejecting additional signed entitlements, so this document does not claim that every build or release permits only those three capabilities.
- `MISSING` release gate: release eligibility requires an exact signed-entitlement allowlist, checked from the final app signature: `com.apple.security.app-sandbox`, `com.apple.security.files.user-selected.read-write`, and `com.apple.security.files.bookmarks.app-scope`, with no additional entitlement unless separately reviewed and documented. Current packaging does not enforce that exact-set rule; release/CI gates must do so before the narrower claim is made ([`release-app.sh`](Scripts/release-app.sh)).
- File access starts from explicit user selection, Finder delivery, or a valid previously approved app-scoped bookmark. A command-line string alone grants no sandbox access. Finder, Dock, recent, external-tool, or extension integrations must pass URLs through validation, dirty-document guards, coordinated I/O, and balanced security-scope lifecycles.
- MacMerge does not install privileged helpers, write system integration state, elevate a shell process, or invoke registration scripts for convenience commands.
- Native actions use structured URL and application APIs. Paths from Finder, recents, Dock items, or extensions must not be reconstructed into an untrusted shell command.
- Compared paths and pair/folder history are sensitive. Recents require documented local retention, stale-item handling, visible clearing, and separation between access bookmarks and user-visible history.
- Opening a file with another app, revealing it in Finder, sharing it, or invoking a Service deliberately discloses its URL and potentially its content to that target. UI and privacy documentation must describe that handoff before broader actions are accepted.
- Extension-controlled instructions must run in a fresh sandboxed out-of-process runner. The runner is signed/versioned, has a narrow typed protocol, receives bounded content rather than paths or capabilities, has no ambient filesystem/network/process access, and fails closed with resource limits and cancellation. No in-process fallback is permitted by the current design.

## Revisit criteria

Revisit a deferred native outcome only when all applicable criteria are met:

1. A concrete workflow and user demand exist; transport-level similarity to WinMerge is insufficient.
2. Required MacMerge compare modes already exist, so Finder, external-tool, recent, or Dock surfaces cannot launch unsupported or misleading tasks.
3. A public macOS API works with sandboxing, code signing, notarization, and supported macOS versions without privilege escalation or unreviewed entitlements.
4. Side ordering, multi-selection limits, invalid or stale URLs, multiple app instances, dirty-document replacement, modifier behavior, and cancellation are specified.
5. Path retention, bookmarks, native documents, pair/folder/project history, Dock visibility, and clearing behavior have privacy review and user-facing documentation.
6. Model tests, UI interaction tests, accessibility checks, signed-entitlement exact-set checks, and installed-app smoke tests cover launch, disabled, failure, and cleanup states.
7. Automation or extension proposals include a threat model, capability model, versioned data contract, fresh out-of-process execution, resource limits, cancellation, auditability, and a deny-by-default network decision.

COM or Windows binary compatibility requires a new, explicitly approved requirement. It is not a default parity target and must not be introduced as an implementation detail of a native adaptation.
